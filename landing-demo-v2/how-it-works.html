它到底是怎么工作的？

可以把 Pangolinfo 想象成给 AI 装一个 App。
这个 App 由三个部分组成——就像一份外卖、一本说明书、一个工具箱。
看完这页你就知道：用户花的 30 秒，到底买到了什么。

想让 AI 变成电商专家，需要 3 个东西配合工作：

🚚 安装小助手 负责"送货上门"——把下面两样自动放好  ·  📘 经验手册 负责"教 AI 怎么想"——10 年运营经验  ·  🧰 工具箱 负责"让 AI 能查数据"——一键拿到 Amazon 真实数据

🚚 第 1 件东西：安装小助手

把它想象成"App Store 一键安装"按钮背后的搬运工人"——用户按一下，它把所有东西自动放好

🚚
安装小助手
让用户 30 秒装好的"搬运工人"
用户只做 2 件事：① 复制一行命令，② 选自己用哪个 AI 助手。剩下全是它干的。

它默默帮用户做了什么

  • 认出用户的电脑是 Mac、Windows 还是 Linux
  • 弹个菜单："你用哪个 AI 助手？"（9 个常见选项）
  • 把"经验手册"放进 AI 能读到的位置
  • 把"工具箱"装好，告诉 AI 怎么用
  • 问："你有 Pangolinfo 账号吗？"——没有的话进入下一步
  • 请用户留个邮箱，自动发验证码过去
  • 用户输入验证码 + 想设的密码，账号就注册好了
  • 自动把账号"会员卡号"存到电脑里，下次 AI 自动用
  • 验证一切正常，告诉用户："好了，重启 AI 就能用"

它不做什么（用户可以放心）

  • 不偷看用户数据——只往电脑里放东西，不传出去
  • 不留后台进程——装完就关，不占内存
  • 代码完全公开——企业 IT 部门可以审计
  • 装完即走——不弹广告、不催更新、不收集行为

没有它的世界 vs 有它的世界

✗ 没有"安装小助手"

用户得自己看好几页文档，找到 AI 助手的安装目录在哪、复制粘贴文件、改一堆配置，然后开浏览器去官网注册账号、点确认邮件、复制密码回来……整个流程 10 多步，普通用户大概率半途放弃。

✓ 有"安装小助手"

用户复制一行字，按回车。看到菜单选"我用 Claude"，输个邮箱，输个验证码，输个密码。30 秒，全程在一个窗口里，连浏览器都不用开。

📘 第 2 件东西：经验手册

把它想象成"老员工传给新员工的工作 SOP"——AI 读完，就知道遇到电商问题该怎么思考

📘
经验手册
10 年运营经验，AI 一次读完
AI 模型本身知识全面但不懂电商业务。手册就是"新员工入职培训资料"——教会 AI 我们公司怎么做事。

手册里写了什么

  • "什么叫蓝海市场？"——告诉 AI 具体看哪几个数字
  • "选品该怎么一步步分析？"——5 步标准流程
  • "哪些坑要避开？"——母婴慎入、3C 先查专利
  • "拿到数据怎么看？"——告诉 AI 哪些指标最重要
  • "什么时候用哪个工具？"——AI 知道该查 Amazon 还是查专利

为什么手册要"看得懂"

  • AI 能读——文本格式，AI 一目了然
  • 用户也能读——感兴趣的人可以打开看，知道我们方法论是认真的
  • 本身是品牌资产——能被搜索引擎收录，等于免费做内容营销
  • 任何 AI 都能用——不限定特定平台
  • 更新方便——改个文字就行，不用重新发版

手册节选 · 长这样（AI 读到的内容）

# 📘 Amazon 选品方法论 ## 怎么判断这是不是蓝海市场？ 满足以下 3 个条件，可以考虑： 1. 月销量 > 300 单，但 Top10 的评论数 < 500 → 有需求，但还没卷起来 2. 价格分布有 $20-$50 的中端空间 → 不会被白牌价格战压死 3. 头部品牌占有率 < 40% → 还有新卖家上位的空间 ## 选品该这样一步步做 第 1 步 搜关键词，看 Top20 都是什么 第 2 步 挑前 10 名，逐个看销量和评论数 第 3 步 抽样看几条 1 星差评，了解痛点 第 4 步 综合判断有没有机会，给结论 ## ⚠ 这几个坑别踩 · 母婴 / 食品：合规门槛太高 · 3C 配件：容易撞专利，先查一下
✗ 没有"经验手册"

AI 虽然知道怎么查数据，但不知道为啥要查、什么顺序查。用户问"帮我选个品"，AI 一脸懵，要么瞎答、要么反问一堆问题。就像给新员工发了一堆账号但没培训，没法独立干活。

✓ 有"经验手册"

用户问"帮我做蓝牙耳机选品"，AI 自动照着手册走 5 步——先搜关键词、再看 Top10、再读差评、再查专利、最后给报告。从"瞎答"升级到"资深运营级别的回答"。

🧰 第 3 件东西：工具箱

把它想象成"老员工桌上的一排按钮——按一下就拿到 Amazon 实时数据"。没有它，AI 只能空谈方法论

🧰
工具箱
让 AI 一键拿到实时数据
手册告诉 AI "该做什么"，工具箱让 AI "能做什么"——查 Amazon、查 Google、查专利，都是按一下按钮的事。

工具箱里有哪些"按钮"

  • 🔍 搜 Amazon 商品——输关键词，返回 Top20 列表
  • 📦 查商品详情——销量、价格、星级、评论数一次给
  • 🏆 看 Bestseller 榜——某个品类的销冠产品
  • 💬 读用户评论——抽样真实评论，看痛点
  • 🌐 查 Google AI 搜索——AI 现在怎么推荐你的品类？
  • ⚖️ 查全球专利——这个产品有专利风险吗？

为什么不让 AI 自己查？

  • AI 容易"瞎填参数"——工具箱强制规范，零出错
  • 账号 Key 自动隐藏——AI 看不到，泄漏不了
  • 查询失败自动重试——AI 不用操心错误处理
  • 只给 AI 它需要的数据——省 AI 算钱（Token）
  • 所有 AI 都能用同一套工具——不用为每个 AI 单独适配

用户提问后 AI 是怎么"按按钮"的（实际工作过程）

# 用户问：帮我做蓝牙耳机选品 # AI 读完手册，开始按按钮： ▸ 按下"搜 Amazon"按钮 关键词: bluetooth earbuds 国家: 美国 → 0.8 秒后: 拿到 Top 20 商品列表 ▸ 按下"查商品详情"按钮 × 10 次 → 拿到每个商品的销量、价格、评论数 ▸ 按下"读评论"按钮 → 抽样 50 条差评，分析痛点 ▸ 按下"查专利"按钮 → 确认主流型号没有专利地雷 # 综合所有数据，AI 给出最终选品报告
✗ 没有"工具箱"

AI 只能"听说"有这些数据，但没法实时拿。它可能编个数字、可能用过时信息、可能让用户自己去 Amazon 查。就像让你不带任何工具去修车——理论懂没用。

✓ 有"工具箱"

AI 当场拿到实时真实数据，回答里出现的销量、价格、评论数都是刚刚从 Amazon 查到的。用户的报告里没有"大约"、"可能"——全是具体数字。这才是"专家级"回答。

🤝 当 Skills 和 MCP 都装上时，Skills 到底干嘛？

这是个核心问题——既然 MCP 已经能让 AI 调用 API，为什么还需要 Skills？

关键真相
Skills 是 MCP 接口说明书的"扩展版"—— 把 MCP tool description 装不下的业务知识、字段含义、使用时机全部写进 Skills。
🧰 MCP 提供（机器层）
  • · 接口的函数签名（参数类型）
  • · 简短一行 description（< 200 字符限制）
  • · 返回 JSON 的字段结构
  • · Schema 强约束 = 调用零拼错
📘 Skills 补充（业务层）
  • · 这个接口什么时候该调用
  • · 返回字段哪个最关键（销量？评论数？）
  • · 多个接口的组合调用顺序
  • · 避坑提示（哪些品类先查专利）
# 举个具体例子 MCP 工具定义（一行 description）: search_amazon(keyword, site) → Top 20 products # ← 限长 200 字，只能这么写 Skills 里关于这个工具的扩展说明: ▸ "selling_rank 字段是销量排名，越小越好" ▸ "review_count < 500 + 月销 > 300 = 蓝海信号" ▸ "site=amz_jp 时，价格单位是日元不是美元" ▸ "调完 search_amazon 后建议串调 get_reviews" # ← 几千字业务知识，MCP description 写不下
💡 所以 Skills + MCP 的真正关系
MCP 让 AI 能调对接口（机器层），Skills 让 AI 知道为什么调、怎么解读（业务层）。 装了 MCP 不装 Skills，AI 是个"会按按钮但不懂业务的实习生"； 两个都装，才是带着 SOP 的资深运营。

💡 我们为什么允许"单装"？
三种方案都需要 API Key——Skills 本质是教 AI 怎么调我们 API 的说明书，最终调用时还是要 Key。
分开装的真正意义是覆盖不同部署场景：
  • 🛡️ 仅 Skills 是企业友好版——纯文本无二进制，企业 IT 部门审查零阻力
  • 🌐 仅 Skills 是网页端唯一选择——Claude.ai Projects / ChatGPT GPTs 装不了 MCP，只能上传 Skills 文件
  • 📖 Skills 本身是知识产品——用户能读、能学、能引用，相当于免费内容营销
  • 🔄 Skills 能引导 AI 用外部 API——把 WIPO 等第三方 API 文档放进 Skills，AI 能直接调（兜底场景）
  • ⚡ 仅 MCP 是开发者友好版——只要精准 API 接口，不要"方法论唠叨"
  • ✨ Both 是日常使用最优解——既懂业务又能办事

老板可能会问的问题

汇报时这几个问题大概率会被追问，提前备好答案

为什么需要 3 样东西？只做 1 样不行吗？
三样东西各管一段，少了任何一个用户体验都崩。

🚚 只有"安装小助手"——没有手册和工具箱，等于"快递只送了空盒子"，啥也用不了
📘 只有"经验手册"——AI 知道该怎么做但没有数据可查，等于"老师傅给你讲了流程但没给你工具"
🧰 只有"工具箱"——有数据没思路，AI 不知道怎么用，等于"给你 Amazon 后台密码但没人教你怎么用"

三个加起来才是完整产品：装得上 + 想得通 + 拿得到。
"经验手册"是文本文件，会被竞争对手抄走吗？
会被抄，但这反而是好事。

手册公开放着，越多人看、越多人引用，搜索引擎越收录我们的方法论——这本身就是免费的内容营销。
而且对手就算抄走手册，还是得用我们的"工具箱"才能拿到真实数据。手册带流量到 API，API 才是真正的护城河。

把它想象成肯德基把炸鸡配方公开——表面上谁都能学，但原料供应链和门店运营才是真本事，没法抄。
"工具箱"装在用户电脑上，会不会占资源？
几乎不占。

工具箱只有 AI 调用它时才会启动，平时安安静静待着，占用约 20MB 内存（相当于一个浏览器标签页的零头）。
它本质上是个"转接员"——AI 说"我要查这个商品"，它就帮 AI 去我们云端查，把结果传回 AI。真正的数据计算都在我们云端，用户电脑只是过个手。
在终端里输密码，用户会不会觉得不安全？
这是程序员圈子里 30 年的标准做法——Git、SSH、各种系统密码都这么输。

用户输入时屏幕不显示密码字符（就像 ATM 取钱），输完直接加密传输到我们服务器，不写电脑硬盘、不留任何痕迹。

相比之下，"让用户跳浏览器注册"反而问题大：
· 用户要切窗口、点确认邮件、复制密码回来——每一步都可能流失
· 行业数据显示，浏览器流程的注册完成率比终端流程低 40%

在终端里完成注册对用户更友好、对我们转化更高。
如果用户收不到验证码邮件呢？
给用户 3 条退路，不会卡死：

① 再发一次——输入 "重发" 重新发送（有防滥用频率限制）
② 换个邮箱——输入"换邮箱"重新填一个
③ 用浏览器——输入"用浏览器"，自动打开官网注册页，复制账号回终端继续

总有一条路能走通。用户不会因为收不到邮件就放弃。
我们数据库不全的领域（比如冷门专利），Skills 能"救场"吗？
能部分救场，但不是主力方案。

当用户查的关键词在我们 ES 数据库里匹配不到完整结果时，Skills 可以引导 AI 做两种降级：

① 模糊匹配兜底——告诉 AI"如果精确匹配失败，可以尝试同义词、上位词、关键词组合"，能查到 70%+ 的相似结果。
② 引导 AI 调外部 API——比如 Skills 里写明"如果我们的 WIPO 接口没数据，可以让 AI 直接调用 WIPO 官方 API（提供文档链接和示例）"，作为长尾覆盖兜底。

但真正的解决方案是补全 MCP 数据源——Skills 救场只是过渡。比如目前 WAP 类专利还在 ES 上未迁移，长期会通过补 MCP 接口解决。
既然 Skills 能让 AI 读外部 API 文档，那为什么还要做 MCP？
这是个好问题——核心答案是 三个差距太大：

① 调用准确率：让 AI 读 API 文档自己拼请求，准确率 70-80%；走 MCP 是 99%+。差距来自 Schema 强约束。
② Token 成本：每次让 AI 重读 API 文档浪费几千 Token；MCP 是结构化函数调用，几十 Token 搞定。调用量大了差几十倍成本。
③ 商业护城河：让 AI 直接调外部 API，我们一分钱都收不到——绕开了我们的鉴权、计费、配额。MCP 是把用户调用沉淀为我们的商业价值的关键入口。

所以 Skills "引导 AI 读外部 API" 只用于兜底场景（我们没覆盖到的长尾数据）。 主流量必须走我们的 MCP——既准又便宜又能商业化。
未来三样东西要更新，会不会很麻烦？
分开管理，互不影响。

📘 "经验手册"更新最频繁——业务方法论迭代，改文字就行，用户一键拉最新版
