为什么需要两条轨道

Skills 和 MCP 解决的不是同一类问题

维度 Skills MCP
解决的问题 教 AI 怎么思考（方法论、判断标准） 让 AI 能执行（API 调用、数据获取）
载体 Markdown 文件 运行中的 server 进程（stdio / SSE）
典型内容 "判断蓝海市场看 3 个信号..." search(keyword, country)
跨 Agent 兼容 需要适配各 agent 的文件格式 JSON-RPC 协议天然统一
调用准确性 依赖 AI 自己拼接 HTTP 请求 Schema 强约束，零拼写错误
性能 AI 推理 + 生成代码 + 执行 直接函数调用，更快
用户可读性 用户能直接看方法论，营销资产 用户看不到内部逻辑
能力定位 复杂工作流、多步推理、领域知识 原子工具调用、实时数据查询

MCP · Write Once, Run Everywhere

一个 server，所有支持 MCP 协议的 agent 都能调

# 你们只需要写一份 MCP server pangolinfo-mcp-server (单一代码库) ↓ 通过 JSON-RPC 协议暴露 tools ├── search_amazon(keyword, country) ├── get_product_detail(asin) ├── get_ai_serp(query) └── search_wipo_patent(...) # 所有支持 MCP 的 Agent 都能调用同一个 server Claude Code ─┐ Cursor ─┤ Hermes ─┤ Windsurf ─┼─→ pangolinfo-mcp-server Cline ─┤ Codex/OpenCode ─┤ OpenClaw ─┘ # 客户端注册路径不同 (install.sh 9 个分支自动处理) Claude Code → ~/.claude/mcp.json Cursor → ~/.cursor/mcp.json Hermes → ~/.hermes/config.yaml Windsurf → ~/.codeium/windsurf/mcp_config.json Cline → VS Code globalStorage settings Codex → codex skill install 命令 OpenClaw → agent.yaml 修改 网页端 → ZIP 打包，手动上传 其他 → 打印路径清单，用户自助

这套架构的 6 个核心价值

🎯 各司其职，不互相挤压

方法论用 Markdown 保留可读性和营销价值，工具调用用 MCP 保证准确性和性能。强行用一种载体做所有事就是缩水。

🚀 跨 Agent 真正通用

MCP 协议是开放标准。一个 server，Claude Code / Cursor / Cline / Windsurf 全部能用，不用为每个 agent 单独适配工具调用代码。

📉 LLM 调用更省钱

结构化工具调用比"读 Markdown → 生成代码 → 执行"路径短得多。同样查询节省 30%+ token，企业级用量差距更显著。

🔒 调用准确性接近 100%

MCP 用 JSON Schema 强约束参数类型。AI 不会再"我以为参数叫 productId 但其实叫 asin"——Schema 自带文档，调用零错误。

🌍 SEO/GEO 资产复用

Skills 是 Markdown，自带 SEO 价值——可发布到博客、知识库、Awesome 列表。同一份内容，分发 + 营销双重收益。

📈 平滑升级路径

未来 API 变化时，只需更新 MCP server，所有 agent 立即生效。不用通知用户重装 skill，长期维护成本极低。
